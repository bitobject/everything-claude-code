## Итог

**Фундамент выбран правильно; менять стек или архитектурный подход не нужно.** Следующие решения
совпадают с тем, что сейчас рекомендуют Three Dots Labs (2024–2025), Ardan Labs (`service`, 2026) и
документация Next.js 16.4, и с тем, как устроены рабочие кодовые базы:
- модульный монолит, модули по бизнес-возможностям, слои внутри модуля;
- правило зависимостей проверяется инструментом;
- порты объявлены на стороне потребителя, зависимости внедряются вручную;
- транзакции через `Update(ctx, id, fn)`, транзакция не передаётся в `context`;
- outbox через River `InsertTx`;
- отдельные модели слоёв; фейки вместо моков;
- тесты на настоящем PostgreSQL через шаблонные базы;
- эталонный модуль как образец для агентов;
- OpenAPI 3.1 contract-first с генерацией обеих сторон;
- Next.js App Router с SSR и Cache Components; Go — единственный владелец бизнес-правил.

Примеры из рабочих кодовых баз: Sourcegraph, Coder, PocketBase и Boundary передают транзакцию явно;
Grafana раскладывает код по фичам и проверяет границы линтером. Все утверждения о версиях Go в STACK.md
§5 верны; все API Next.js 16.4 из наших примеров существуют в опубликованных пакетах.

**Что не так — четыре класса проблем:**
1. **Ошибки в эталоне и примерах, которые агенты будут копировать** — 18 штук (раздел 1). Самые серьёзные:
   - ответ на неверный запрос возвращает введённые данные, включая телефон;
   - форма заявки стирает ввод при ошибке;
   - `Update` молча теряет изменения;
   - пример формы шлёт поле, которого нет в контракте.
2. **«Проверяется инструментом» там, где не проверяется:**
   - go-arch-lint не видит стандартную библиотеку;
   - правило «модуль читает только свою схему» ничем не проверяется;
   - на фронте границы не проверяются вовсе;
   - «готово» держится на дисциплине: CI нет.
3. **Не описано то, на чём модульные монолиты ломаются при росте:**
   - публичный API модуля;
   - события с несколькими подписчиками — описанная схема на River не работает;
   - чтения между модулями;
   - согласованность между модулями (продажа лида = назначение + списание).
4. **Пробелы:**
   - TS-клиент API в режиме поддержки, без обновлений безопасности, — нужна замена;
   - эксплуатация: бэкапы, readiness, аудит, наблюдаемость;
   - 152-ФЗ: согласия, локализация всех хранилищ, включая логи и бэкапы;
   - слой экспертности для юридической тематики (YMYL) в SEO;
   - политика обновления зависимостей.

Избыточного мало:
- одинаковая «полная» форма модуля даже для простых справочников;
- тройное преобразование данных на каждом чтении;
- FAQPage-разметка на тысячах страниц (поисковики её больше не используют);
- все 14 агентов на самой дорогой модели;
- остатки форка.

## 1. Ошибки — исправить в первую очередь

### 1.1. Ответ 400 возвращает введённые данные и дамп схемы — [проверено]
**Где:** `reference/backend/cmd/api/main.go` (`Detail: err.Error()` в обработчике ошибок валидатора) и
`internal/platform/httpserver/problem.go` (`BadRequestWriter`).

**Что происходит** (тест на копии эталона):
- при неверном телефоне `detail` содержит `'+7999123456X' does not match pattern …` и блок `Value:`;
- при лишнем поле `detail` содержит всё тело запроса, включая корректный телефон, и полную JSON-схему.

Это попадает в ответ клиенту и в логи прокси, то есть нарушает наше же правило о персональных данных.

**Причина:** для OpenAPI 3.1 kin-openapi работает в режиме JSON Schema 2020-12, а
`DisableSchemaErrorDetails` в этом режиме отключён.

**Исправление:**
- фиксированный `detail` и ошибки по полям `errors: [{pointer: "#/phone", code: "pattern"}]` из
  `JSONPointer()`/`SchemaField` (без `Reason`, где есть значения);
- `MultiError: true`;
- тест «отправленное значение не появляется в ответе»;
- то же для `BadRequestWriter`.

Независимо нашли трое исследователей: API, код Go, безопасность.

### 1.2. Форма заявки стирает ввод при ошибке — [проверено]
**Где:** `skills/nextjs-patterns/SKILL.md` («Server Actions and forms») и тест в `agents/e2e-runner.md`.

**Что происходит:** React 19 после завершения action сбрасывает неконтролируемые поля. Документация:
«Returning a validation error instead of throwing also triggers this reset». У наших полей нет
`defaultValue`. Тест называется «…without losing input», но значения не проверяет, поэтому проходит.

**Исправление:** в состояниях ошибки возвращать `values` и подставлять их в `defaultValue`; в тесте
проверять `toHaveValue` с JavaScript и без него.

### 1.3. Пример формы не соответствует контракту — [проверено]
**Что происходит:**
- форма отправляет поле `name`, которого нет в `CreateLeadRequest`; при `additionalProperties: false`
  это 400 на каждую заявку;
- регулярное выражение для телефона пропускает `8 (999) 123-45-67`, который контракт отклоняет;
- zod-схема написана вручную и расходится с контрактом, хотя STACK.md сам называет DTO, повторяющие API,
  ошибкой.

**Исправление:**
- генерировать zod из контракта (это умеют генераторы из решения C1) либо собирать тело запроса из
  разобранных полей после нормализации телефона;
- тест, прогоняющий вывод формы через валидатор.

### 1.4. `Update(fn)` сохраняет только статус — [проверено]
**Где:** `reference/.../repository/postgres/repository.go` (запрос `UpdateLeadStatus`); то же в `postgres-patterns`.

**Что происходит:** любое другое изменение агрегата внутри `fn` молча теряется. Фейк в тестах use case
хранит указатель, меняет объект на месте и не откатывает изменения при ошибке `fn`, так что тесты этого
не поймают. При этом `/ecc:new-module` велит агентам копировать эталон.

**Исправление:**
- запрос `UpdateLead`, который пишет все изменяемые колонки;
- интеграционный тест «все поля переживают `Update`»;
- фейк хранит копии и фиксирует их только при успехе.

### 1.5. go-arch-lint не проверяет стандартную библиотеку — [проверено]
**Проверка:** `net/http` и `database/sql` в `usecase` → `make arch` зелёный. В исходнике go-arch-lint
импорты стандартной библиотеки всегда разрешены.

**Почему это ошибка:** STACK.md утверждает, что внутренние слои «никогда не видят `net/http`» и это
«enforced by go-arch-lint». Кроме того, ничем не проверяются struct-теги в сущностях и вызовы `Restore*`
вне репозиториев.

**Исправление:**
- правила depguard (он уже есть в golangci-lint) для `entity` и `usecase`: стандартная библиотека без
  `net/`, `database/`, `os`, `log`;
- тест в стиле `go/build/deps_test.go` для тегов и `Restore*`.

### 1.6. «Модуль читает только свою схему» ничем не проверяется — [проверено]
**Что происходит:** все записи sqlc используют `schema: migrations`, то есть видят таблицы всех модулей.
Запрос модуля `leads` к `billing.*` компилируется и проходит `make check`.

**Исправление:** проверка в `make check` (правило `sqlc vet` или тест по `queries/*.sql`); позже —
отдельная роль БД на каждый модуль.

### 1.7. Асинхронная связь модулей не работает так, как описана — [проверено]
**Что описано:** «A ставит задачу — B реагирует».

**Что происходит:**
- `river.AddWorker` паникует на повторном kind, то есть у задачи ровно один обработчик. Двум подписчикам
  (биллинг, уведомления) нужны две задачи — и модуль A должен знать своих подписчиков;
- тип задачи лежит в `usecase` модуля A, а импортировать его модулю B запрещено;
- вендора River нет в `.go-arch-lint.yml`: первый же `InsertTx` или воркер упрётся в проверку, а
  правило запрещает расширять конфиг.

**Исправление:** решение B2. Вендор `river` в конфиг — сразу.

### 1.8. Аргументы задач River — JSON без тегов — [источники; хранение в JSON проверено]
**Что происходит:** теги во внутренних слоях запрещены. Если переименовать поле, задачи, которые уже в
очереди или ждут повтора (25 попыток — около трёх недель), получат нулевые значения.

**Исправление:**
- документированное исключение: `json`-теги у аргументов задач;
- поля только добавлять;
- golden-JSON тест на каждый kind;
- в аргументах только ID, без персональных данных.

### 1.9. TS-клиент API в режиме поддержки — [проверено: issue #2874]
openapi-typescript, openapi-fetch и openapi-react-query с 19.09.2026 в «maintenance mode»: обновлений
не будет, включая обновления безопасности. Передавать проект автор не станет и прямо ссылается на атаки
shai-hulud. Последний релиз вышел 11.02.2026, TypeScript 7 не поддерживается. До замены текущие версии
работают на TS 6.0. Что делать — решение C1.

### 1.10. CSP с nonce несовместим со статическими SEO-страницами — [проверено: документация в пакете next@16.4.6]
`security-review` требует CSP на nonce, а документация Next говорит: «all pages must be dynamically
rendered», «Partial Prerendering (PPR) is incompatible». Агент, следующий правилу, либо сделает тысячи
страниц динамическими, либо сломает CSP. Что делать — решение F1.

### 1.11. LCP-картинка остаётся ленивой — [проверено: `get-img-props.js`]
Совет «только `fetchPriority="high"`» повторяется в `nextjs-patterns`, `seo`, `rules/typescript.md` и
`typescript-reviewer`. Но `next/image` всё равно ставит `loading="lazy"`.

**Исправление:** `loading="eager"` вместе с `fetchPriority="high"` (или `preload`).

### 1.12. `(await cookies()).toString()` меняет значения cookie — [проверено: исходник `@edge-runtime/cookies`]
**Что происходит:**
- при разборе значения декодируются, а не декодируемые молча отбрасываются;
- при сборке строки они кодируются обратно через `encodeURIComponent`;
- Go значения cookie не декодирует, поэтому токен с `+`, `/` или `=` не будет узнан.

**Исправление:** пересылать сырой заголовок (`(await headers()).get('cookie')`) или только сессионную
cookie из него.

### 1.13. Метрика работает в кабинете — [проверено: в seo-скилле «render once in the root layout»]
**Что происходит:** корневой layout оборачивает и кабинет. Сторонний скрипт видит телефоны клиентов в
DOM и может делать запросы к `/api` с cookie юриста. Это противоречит `security-review`.

**Исправление:**
- Метрика только в `(public)` и за переключателем согласия;
- выключить «дополнительные настройки отслеживания», «маскированные данные» и запись всех полей
  Вебвизора;
- `ym-disable-keys` на полях формы.

### 1.14. Ошибки HTTP логируются и отображаются неправильно — [проверено]
**Что происходит:**
- `ErrorWriter` не логирует «известные» ошибки: 503 (`KindUnavailable` — дедлоки, таймауты блокировок)
  не оставляют следа;
- обрыв соединения клиентом (`context.Canceled`) пишется как ERROR и получает 500;
- адаптер оборачивает ошибку разбора уже сохранённых данных через `%w`, и битый телефон в БД уходит
  клиенту как 422 `lead.invalid_phone`;
- `exhaustive.default-signifies-exhaustive: true` позволяет новому `Kind` молча стать 500.

**Исправление:**
- логировать по статусу: ≥500 — ERROR, 503 — WARN, 4xx — не логировать, `Canceled` — DEBUG и без 500;
- в адаптере переводить ошибки разбора в внутренние;
- `default-signifies-exhaustive: false` и тест «у каждого `Kind` есть статус».

### 1.15. Миграции идут с пулом, таймаутами и ролью приложения — [проверено: `migrate` берёт тот же `DATABASE_URL`]
**Что происходит:**
- `statement_timeout` приложения (5 с по скиллу) убьёт `CREATE INDEX CONCURRENTLY`. Останется
  INVALID-индекс, а повторный запуск с `IF NOT EXISTS` его пропустит;
- у рабочей роли есть права на DDL;
- `lock_timeout` для миграций в эталоне не задан;
- миграции River идут без блокировки.

**Исправление:**
- отдельное подключение `MIGRATE_DATABASE_URL` под ролью-владельцем схем, `lock_timeout=5s`,
  `statement_timeout=0` (или 1 час);
- после `Up` проверять, что не осталось INVALID-индексов;
- рабочей роли — только DML;
- миграции River — как goose-миграции: одна история, одна блокировка, squawk их проверяет.

После этого выключенные сейчас правила squawk о таймаутах станут честными: так сделано в `lead`.

### 1.16. sqlc понимает грамматику PostgreSQL 17, а не 18 — [проверено]
**Проверка:** релизный sqlc 1.31.1 собран с pg_query_go v6.2.2 и `CGO_ENABLED=0`.

**Что происходит:** синтаксис PG18 в миграциях сломает `sqlc generate`: виртуальные генерируемые колонки,
`NOT ENFORCED`, `WITHOUT OVERLAPS`, `RETURNING old/new`. Заодно устарела фраза «sqlc требует cgo» в
`postgres-patterns`. В STACK.md я исправил её в своём новом абзаце.

**Исправление:** правило «сервер — PG18, но файлы, которые читает sqlc, пишем в диалекте PG17»;
у генерируемых колонок всегда `STORED`.

### 1.17. Время обработки запроса ничем не ограничено — [источники; поведение `WriteTimeout` известно, golang/go#59602]
**Что происходит:** `WriteTimeout` не отменяет контекст обработчика. `statement_timeout`, который требует
скилл, в эталонном `postgres.Open` не задан. В итоге запрос держит горутину и соединение уже после того,
как ответ отправить нельзя.

**Исправление:**
- middleware с `context.WithTimeout` внутри `Recover`;
- `DeadlineExceeded` → 503/504;
- привести `postgres.Open` в соответствие со скиллом.

### 1.18. Остановка без «слива» трафика — [проверено: `Run` сразу вызывает `Shutdown`]
**Что происходит:** есть только `/healthz`. Заявки, пришедшие во время деплоя, теряются.

**Исправление:**
- `/livez` и `/readyz` (пинг БД не дольше 1 с);
- по SIGTERM сначала провалить readiness, выждать время снятия с балансировщика, потом `Shutdown`;
- River останавливать мягко.

### B. Бэкенд: дополнения без смены подхода
- **B1. Публичный API модуля.** Пакет `internal/<m>/contract`: фасад для других модулей, DTO, события.
  Шлюзы и воркеры зависят только от него. Граф зависимостей модулей (без циклов) — в документации и в
  конфиге линтера. *Да: сейчас это дёшево, потом дорого (так считают трое исследователей).*
- **B2. События между модулями.** Модуль публикует версионированные события в `contract`. Диспетчер в
  `platform` в той же транзакции раскладывает событие по задачам подписчиков (`InsertManyTx`); подписчиков
  регистрирует `cmd`. Модуль A не знает своих подписчиков. *Да.*
- **B3. Два профиля модуля.**
  - Полный — если есть хотя бы одно: жизненный цикл или машина состояний; деньги или юридические
    обязательства; инварианты на нескольких полях или агрегатах; несколько входов (HTTP, задачи, другие
    модули); около 10 и больше сценариев.
  - Тонкий — для остального (справочники городов и тем, контент): один пакет с обработчиками, функциями
    сервиса и sqlc; своя схема и публичный API сохраняются.
  - `/ecc:new-module` спрашивает профиль и обоснование границы.

  *Да.*
- **B4. CQRS-lite.** Запись идёт через сущности, чтение — через query-порты прямо из sqlc в
  view-структуры, без `Restore` и тройного преобразования. SEO-страницы и списки кабинета — в основном
  чтения. *Да.*
- **B5. Согласованность между модулями (продажа лида).** Варианты:
  - (а) денежный инвариант живёт в одном модуле;
  - (б) сага на задачах River с идемпотентными шагами и компенсациями;
  - (в) осознанная общая транзакция, как `NewWithTx` у Ardan.

  *Выбор сделать при проектировании billing. Уже сейчас — правило «внутри `Do`/`Update` только свои
  репозитории, никаких вызовов других модулей», иначе пул может заблокироваться.*
- **B6. Тесты через реальный стек.** Роутер → обработчики → сценарии → sqlc → PostgreSQL. Плюс контрактные
  тесты фейков: один набор прогоняется и против фейка, и против адаптера. *Да: так устроены тесты во всех
  рассмотренных рабочих кодовых базах.*
- **B7. Упаковка модуля.** *Спорно.* Варианты:
  - (а) как сейчас: одинаковые `entity/usecase/postgres` в каждом модуле, при импорте нужны алиасы;
  - (б) имена с префиксом модуля, как у Ardan: `leadapp`, `leadpg`, `leadhttp`;
  - (в) внутренности под `internal/<m>/internal/…`, а корневой пакет модуля — фасад (`New(deps)`,
    HTTP-обработчик, контракт). Тогда импорты внутренностей запрещает сам компилятор, и конфиг
    go-arch-lint перестаёт расти на шесть компонентов с каждым модулем.

  *Рекомендую (в) вместе с B1 и решить до первого настоящего модуля.*
- **B8. Интерактор на модуль или тип на сценарий** (`AssignLead{…}.Handle`). *Спорно, в Go встречаются
  оба.* *Рекомендую тип на сценарий для полных модулей: в тестах меньше общих зависимостей, при
  параллельной работе агентов меньше конфликтов.*
- **B9. Интерфейсы сценариев в delivery** (`LeadUseCases`) **и их фейки.** Заменить реальным интерактором
  с фейковыми портами ввода-вывода. *Спорно: стоимость против изоляции.* *Рекомендую да, вместе с B6.*

  - интеграционные тесты: локально `-short` их пропускает, в CI они падают при отсутствии БД.

  *Да.*

## 3. Архитектура бэкенда: что говорят лучшие практики

**Школы (исследователь 1):**
- Go-команда никакой слоистости не предписывает, поэтому «строгая» Clean Architecture — защитимый выбор
  команды, а не консенсус Go.
- Внутри модуля наш подход — это DDD-lite Clean Architecture Three Dots Labs. Ardan Labs в `service`
  (2026; там уже есть скиллы для агентов) пришли к тем же идеям под другими именами.
- Школы сходятся в главном: верхний уровень по предметной области, маленькие интерфейсы у потребителя,
  явная сборка зависимостей в `main`, отдельные модели слоёв с явным преобразованием, когда приложение
  большое.
- Расходятся в трёх местах:
  - слои внутри домена: Cheney и Edwards за меньшее число крупных пакетов;
  - сущности: Three Dots инкапсулирует, Ardan и Johnson держат простые данные;
  - сценарии: тип на сценарий у Three Dots, сервисная структура у Ardan и Edwards.

**Практика (исследователь 2, 14 кодовых баз):**
- полная Clean/Hexagonal-слоистость встречается только в учебных репозиториях (wild-workouts,
  monolith-microservice-shop);
- рабочие системы раскладывают код по фичам (Grafana, Boundary, Kratos) или по слоям с подпакетами фич
  (Mattermost, Gitea, Harbor, Ardan);
- модули зависят от API, который публикует модуль-поставщик;
- тесты опираются на реальную БД;
- Mattermost показывает цену слоёв на верхнем уровне: пакет `app` — 171 файл, интерфейс хранилища —
  около 1 000 методов.

**Критика, которая к нам относится:**
- сквозные слои на чтениях (Ousterhout, «pass-through methods»);
- интерфейсы-зеркала сценариев для обработчиков;
- размножение преобразований: четыре модели и около восьми мест правки на каждое новое поле;
- одинаковые имена пакетов и экспортируемый `Restore*`.

**Критика, которая не относится:** DI-фреймворки и рефлексия, интерфейсы у производителя, generic-репозитории,
«абстракция БД для замены», транзакции через `context`, слои на верхнем уровне.

**Транзакция в `context`** — спорный вопрос, а не решённый:
- Avito go-transaction-manager, Ory Kratos и Harbor передают её в контексте;
- Three Dots называет это «маскировкой проблемы»;
- Gitea пришлось добавить проверку во время выполнения, чтобы ловить ошибки такого подхода.

Наш выбор — явная транзакция — для кода, который пишут агенты, надёжнее.

**Вывод исследователей 1–3:** оставить модульный монолит и внутреннее правило зависимостей для модулей с
настоящей логикой; упростить остальное (B3, B4, B9); добавить то, что держит границы между модулями
(B1, B2, B5).

| Репозиторий | Устройство | Зависимости между модулями, транзакции, тесты |
|---|---|---|
| wild-workouts (Three Dots) | Clean/hexagonal по сервисам; `users` — один плоский пакет | порты у потребителя; `UpdateFn`; компонентные тесты |
| ardanlabs/service | слой, затем домен (`xapp`, `xbus`, `xdb`) | `productbus` импортирует `userbus`; транзакция из middleware через `NewWithTx`; API-тесты на реальной БД |

## 4. Большие системы и процесс с ИИ-агентами

**Подтвердилось:**
- монолит сначала, выделение сервиса — только по измеримой причине (Fowler, Grzybek);
- модули по бизнес-возможностям (Simon Brown, Spring Modulith);
- схема на модуль, без внешних ключей и чтений между модулями (Grzybek, Jovanović, Vernon);
- шлюз на стороне вызывающего как антикоррупционный слой;
- outbox на River;
- go-arch-lint, squawk и проверка инструментов как fitness functions («Building Evolutionary Architectures»);
- фейки вместо проверки взаимодействий («Software Engineering at Google», гл. 13);
- эталонное приложение как якорь для агентов (Thoughtworks Radar vol. 35 — Trial [источники]);
- короткий CLAUDE.md и правила по путям;
- «план → вопрос вместо догадки → TDD, тесты не ослаблять» (документация Claude Code, Kent Beck 2025).

**Не хватает:**
- **Стратегического проектирования:** карта поддоменов (ядро — маршрутизация и продажа лидов;
  вспомогательные — профили юристов и каталог контента; общие — идентификация, платежи, SMS), карта
  контекстов, глоссарий модуля, диаграммы C4 (контекст и контейнеры).
- **Политики данных между модулями:**
  - у справочных данных (города и темы управляют SEO, маршрутизацией и ценой) должен быть владелец;
  - копии только для чтения или снимки (цена на момент продажи);
  - персональные данные не копируются; удаление распространяется событиями.
- **Маленьких изменений и частой интеграции:** около 100 строк — нормальный размер по Google; слияние в
  основную ветку не реже раза в день (DORA); незаконченное — за флагами.
- **Пути выделения модуля в сервис** (позже): шлюз → клиент по контракту, диспетчер → брокер, схема →
  своя БД.
- **Оценки самой «обвязки» агентов** (позже): `claude plugin eval` на ключевых сценариях — межмодульный
  вызов даёт порт и шлюз, задача ставится через `InsertTx`, на неоднозначный запрос агент задаёт вопрос.

**Избыточно:**
- веер ревьюеров на каждое изменение;
- все агенты на opus;
- `/ecc:orchestrate` с прозаическими передачами между агентами;
- `eval-harness` для детерминированных функций — их уже проверяют тесты.

## 6. Данные

**Подтвердилось:**
- `Update(fn)` по умолчанию, провайдер транзакций — для редких случаев; Three Dots называет `UpdateFn`
  «go-to solution»;
- River — лучший выбор для outbox в Go + PostgreSQL: Hatchet, Asynq и Temporal не умеют ставить задачу в
  той же транзакции;
- goose (Atlas lint с v0.38 только в Pro; golang-migrate, tern, dbmate ничего не добавляют);
- таблица безопасных изменений схемы; таймауты приложения; явные списки колонок; именованные ограничения;
  keyset-пагинация;
- UUIDv7 из stdlib; схема на модуль.

**Добавить (кроме пунктов раздела 1):**
- **Политика ошибок воркеров:** `NotFound`, `Invalid` и `Conflict` → `river.JobCancel`, остальное
  повторять. Иначе удалённый лид будет повторяться неделями.
- **UnitOfWork без savepoint:** репозиторий, созданный на транзакции, работает прямо в ней. Каждый
  savepoint — два лишних запроса, и GitLab отказался от них из-за подвисаний на репликах. Чтения внутри
  `Do`, по которым принимается решение, должны блокировать строку.
- **sqlc:**
  - `omit_unused_structs: true`;
  - правила `sqlc vet`: `db-prepare` на своём PG18 и «своя схема»;
  - `sqlc verify` не использовать: он отправляет схему в облако sqlc.
- **Таблица безопасных миграций:** уникальность через `CREATE UNIQUE INDEX CONCURRENTLY` +
  `USING INDEX`; хранимые генерируемые и identity-колонки переписывают таблицу; «одна DDL на горячую
  таблицу в файле».
- **Таймауты и тестовая БД:**
  - `transaction_timeout` (PG17);
  - пул считать от vCPU базы;
  - тестовый образ не alpine, если продакшен сортирует кириллицу через glibc-локаль.
- **Деньги между модулями:** идемпотентный потребитель (`UNIQUE(lead_id)` у строки списания,
  `ON CONFLICT DO NOTHING`), баланс через `UPDATE … WHERE balance >= $2` или журнал проводок.
- **Персональные данные в таблицах River:** завершённые задачи хранятся сутки, отброшенные — 7 дней,
  вместе с текстом ошибок. Не класть туда персональные данные; задача удаления или обезличивания лидов.

Подробно: [`05-data.md`](2026-11-13-sources/05-data.md).

## 7. API-контракт

**Подтвердилось:**
- contract-first OpenAPI 3.1 остаётся лучшим выбором для этого продукта. Альтернативы проигрывают:
  - Huma — спецификация становится выходом бэкенда;
  - TypeSpec — лучше для авторинга на большом масштабе, но добавляет инструмент (вариант на потом);
  - ConnectRPC — лучшая кодогенерация, но RPC-пути хуже подходят для партнёрского REST;
  - GraphQL — ничего не даёт;
- 3.1, а не 3.2: oapi-codegen v2 не поддерживает 3.2;
- все Go-версии свежие; nethttp-middleware v1.3.1 передаёт обработчику уже проверенное тело;
- центральное преобразование ошибок в статусы;
- клиент ветвится по стабильному `code`;
- непрозрачный курсор; персональные данные не в URL;
- даты в RFC 3339 UTC, деньги в минимальных единицах;
- «расширяемые» enum; правила совместимости.

**Добавить (кроме C1–C5):**
- **Безопасность в контракте:** `securitySchemes` и глобальный `security`, публичные операции явно с
  `security: []`. Без функции аутентификации kin-openapi отклонит запрос, то есть «забыть проверку»
  станет невозможно.
- **Заголовки и коды в контракте:** `ETag`, `If-Match`, `Location`, `Retry-After`; `429` на публичных
  операциях.
- **Порядок деплоя:** закрытые тела запросов (`additionalProperties: false`) требуют выкатывать бэкенд
  раньше фронта. В `allOf` вместо этого — `unevaluatedProperties: false`.
- **Подмножество 3.1:** поддержка 3.1 в oapi-codegen «начальная» (с v2.8.0), поэтому ограничить
  контракт подмножеством, которое проверяет линт.
- **Позже:**
  - моки (Prism или MSW);
  - Schemathesis;
  - разбиение спецификации или переход на TypeSpec;
  - заголовки `Deprecation`/`Sunset`;
  - отдельный контракт для партнёров;
  - `nullable-type` до первого PATCH.

Подробно: [`06-api-contract.md`](2026-11-13-sources/06-api-contract.md).

## 8. Фронтенд

**Архитектура — подтвердилось:**
- Server Components по умолчанию;
- Go — единственный авторитет; Next пересылает cookie, но не авторизует; `proxy.ts` — не граница
  авторизации;
- папки фич вне `app/`; `'use client'` на листьях; `server-only`;
- `'use cache'` с тегами над удалённым API и вебхук инвалидации; TanStack Query только в кабинете;
- браузер ходит на `/api` того же origin;
- ожидаемые ошибки — значениями, неожиданные — в `error.tsx`;
- асинхронные Server Components проверяются e2e;
- `strict` и `noUncheckedIndexedAccess`;
- ESLint + Prettier без монорепозитория.

**Корректность — подтвердилось.** Сверено с исходниками и документацией в пакетах:
- `cacheComponents`, `ensureStatic` (значения, область, ошибки), `cacheLife`, `cacheTag`, `revalidateTag(tag,'max')`, `updateTag`;
- `proxy.ts`, `generateStaticParams`, `generateSitemaps`;
- поля Metadata API; `other` в robots для Clean-param;
- поведение `notFound()` и `redirect()` при стриминге;
- htmlLimitedBots (включает Яндекс);
- API openapi-fetch и openapi-react-query, zod 4, Playwright 1.65, конфиг ESLint 10;
- утверждения о TS 7 (peer-зависимости typescript-eslint и openapi-typescript).

Подробно: [`08-frontend-correctness.md`](2026-11-13-sources/08-frontend-correctness.md).

**Не хватает (кроме D1–D7):**
- **Устойчивость серверного клиента API:** таймаут `AbortSignal.timeout` и заголовки request-id/`traceparent`.
- **Расхождение версий при деплое:** ID Server Actions меняются с каждым деплоем, и страница, открытая до
  деплоя, получает «Failed to find Server Action». Форме нужен путь повтора без потери ввода.
- **Инструменты:** knip в pre-PR и CI; `typedRoutes: true`; `wcag22aa` в проверках axe (сейчас только 2.1).
- **Пины и окружение:**
  - Node и pnpm в `engines`/`devEngines`;
  - закрепить вспомогательные пакеты: @axe-core/playwright, vite, @vitejs/plugin-react, jsdom,
    @testing-library/react, @tailwindcss/postcss;
  - `next build` проверяет типы через `tsc` проекта, включая e2e и тесты.
- **Прокси и ссылки:**
  - Next сравнивает `Origin` с `x-forwarded-host`/`host`, поэтому прокси должен передавать публичный
    хост, иначе нужен `serverActions.allowedOrigins`;
  - неизвестные slug под `ensureStatic` вызывают блокирующий рендер и запрос в Go — проверять slug в
    `proxy.ts`.
- **Тестируемость:** асинхронный контейнер передаёт props синхронному представлению; чистые функции
  разбора и преобразования Problem; MSW 3 + openapi-msw.

**Не брать:** полный Feature-Sliced Design (много церемоний для маленькой команды), taint API (экспериментальные),
`exactOptionalPropertyTypes` (конфликтует со сгенерированными типами), Storybook и монорепозиторий сейчас.

Подробно: [`07-frontend-architecture.md`](2026-11-13-sources/07-frontend-architecture.md).

- авторизация на уровне объектов в сценариях: 404 на чужие ID, фильтр по владельцу в SQL, негативные тесты;
- непрозрачные серверные сессии с ротацией и отзывом; правила OTP;
- `CrossOriginProtection` в своих реальных пределах;
- `proxy.ts` не граница авторизации (урок CVE-2025-29927);
- у Next нет доступа к БД, поэтому RCE в RSC и Next в 2025–2026 годах наносят меньше вреда;
- настройка нескольких инстансов (`cacheHandlers`, ключ шифрования Server Actions, `deploymentId`);
- версии уже содержат исправления Next и React октября–ноября 2026;
- govulncheck и gosec; правило 14 дней с исключением для исправлений безопасности.

**Добавить (кроме F1–F8):**
- **Ревьюер:** сейчас он отбрасывает находки «без пути эксплуатации». Нужен отдельный раздел «соответствие
  и укрепление», иначе отсутствие согласий, аудита и бэкапов не попадёт в отчёт.
- **Роли БД:** роль-владелец для миграций, роль приложения только с DML, на таблицы аудита только INSERT;
  SCRAM вместо MD5 (в PG18 MD5 устарел); `sslmode=verify-full` для БД на другом хосте.
- **Заголовки:** `nosniff` и `Cache-Control: no-store` на `/v1/*`, иначе одно правило кэша на прокси
  отдаст лиды юриста A юристу B; `Clear-Site-Data` при выходе.
- **SSRF:** проверять адреса в `net.Dialer.Control`, иначе пройдёт DNS rebinding.
- **Укрепление Next при самостоятельном хостинге:**
  - прокси отбрасывает неизвестные `Host`;
  - контейнер без root, с файловой системой только для чтения;
  - ограничить оптимизатор картинок: в октябре 2026 была критичная RCE в sharp [источники];
  - один инстанс Next, пока нет общего хранилища кэша.
- **Позже:** отдельный origin для кабинета; шифрование колонок телефона и вопроса со слепым индексом
  (насчёт ГОСТ — к специалисту); SBOM; DAST; Semgrep для TS.
